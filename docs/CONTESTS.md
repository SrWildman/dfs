# The contests engine

`src/dfs/contests/` learns **which contests suit which lineups** and **how your fields build theirs**, from the
two DraftKings files you download by hand and from public nflverse data. Pure Python: no sheet, no credentials,
and **no DraftKings network call of any kind** (standing rule). `dfs contests analyze` is the one command; it is
hidden (`hidden=True`, like `dfs model`) and not in `docs/COMMANDS.md` or the launcher until it is wired into
`dfs week close`. Everything below was built and tested on **synthetic files that match the real formats**
(`tests/contests/fixtures/`, made-up usernames, regenerated by `tests/contests/build_fixtures.py`); no real
DraftKings file has been seen by this code yet.

## Read this first: the slate index does not yet predict your cash lines

The task asked for the slate-scoring index that **best predicts** your five typed Results `Cash Line`s (GIANT
$25 Double Up, 2026 weeks 1-5). **None of the candidates does, including one extra I tried.**

| Week | Cash line | `top_n_lineup` | `p95_optimal` | `points_per_game` |
|---|---|---|---|---|
| 1 | 147.56 | 1.068 | 1.073 | 1.163 |
| 2 | 140.16 | 0.918 | 0.922 | 0.796 |
| 3 | 158.70 | 1.022 | 1.004 | 1.027 |
| 4 | **105.98** | 1.008 | 1.011 | 0.979 |
| 5 | 153.06 | 0.984 | 0.990 | 1.035 |

(the three right-hand columns are each candidate relative to its 2026 mean over weeks 1-5)

| Candidate | r | R² | Spearman | leave-one-out RMSE | RMSE of "just predict the mean" |
|---|---|---|---|---|---|
| `top_n_lineup` | 0.10 | 0.01 | 0.3 | **24.0** | 23.2 |
| `p95_optimal` | 0.02 | 0.00 | -0.1 | 24.4 | 23.2 |
| `points_per_game` | 0.26 | 0.07 | 0.5 | 27.2 | 23.2 |

Every candidate does *worse* than knowing nothing (the last column), which is what five points and no
relationship look like. The driver is **week 4**: the cash line was 105.98, 40+ points under every other week,
on a slate that is average by every public measure (all three candidates sit within 2% of their mean). I also
tried a fourth idea outside the three (the realised score of the lineup of players with the best *prior*
form, to measure whether "the popular players hit"); it correlated 0.09 with the cash lines too, so it is not
in the code.

What I did, and what needs your call:

- `slate_index.SELECTED = "top_n_lineup"` because it has the lowest leave-one-out error of the three (a
  difference of 0.4 points, i.e. nothing). **Treat the index as unvalidated.** The toughness code takes it as
  an input, and `--slate-index none` (raw points) is one flag away; with a non-predictive index, dividing by
  it only adds noise of about ±7% (the candidates' own week-to-week spread).
- **Please check the week 4 `Cash Line` you typed** (is it the same contest and slate as the others?). Dropping it
  does not rescue the fit, though: on the other four weeks r is 0.4-0.5 but the leave-one-out RMSE (15-19) is
  still worse than predicting the mean (9.1). `slate_index.fit_candidates(table, cash_lines)` takes any dict, so
  re-fitting after a correction is one call.
- A second possibility is that the GIANT $25 Double Up's slate is not the Sunday-afternoon one I index
  (`Contest_Date_EST` in your history tells you which slate it started on).
- Re-run the fit once you have more weeks, or with the real `Cash Line`s of 2021-2025 if you have them.

## The two input files

**1. Contest-entry history** (My Contests -> History). One CSV, UTF-8 BOM, 14 columns
(`Sport ... Places_Paid`), the whole account every time. `history.py` keeps every column verbatim as text
(`$8.00`, `2,972`), deduplicates by `Entry_Key` (the export merged last wins), drops non-NFL rows (counted in
`MergeResult.dropped_other_sports`), and adds `Season`, `Week`, `Slate`, `Series`, `Format`, `Matchup`,
`Opponent`, `Entry_No`, `Entry_Max`, `Bankroll_Class`, `Format_Class`. `merge_into(log, export)` is safe to
re-run; exports must be merged **oldest first**, since the last one merged wins.

**2. Per-contest "export full standings"** (`contest-standings-<id>.csv`, bare or in a zip of any name, found
recursively in the `--standings` folder). `standings.py` returns the entries (rank, points, name with `(1/3)`
split off), the score profile, the parsed lineups and (via `ownership.parse_ownership_export`, called as is)
the ownership table. 0-byte files are skipped and listed; a second file for the same contest id is listed and
ignored; a lineup that is not exactly 9 slots (Classic) or CPT + 5 FLEX (Showdown) is reported with its reason
in `lineup_errors.csv` and never guessed. DraftKings serves standings for about two weeks, so download them
promptly: nothing else keeps them.

## Series and formats (`series.py`)

A **series** is a contest's name with the entry counter `(2/5)`, the Showdown matchup `(BUF @ LAR)` and the H2H
opponent stripped (`NFL $1 srwildman vs. rival` -> `H2H $1`; `DREAMERS DFS  by bradikal36 #5` -> `DREAMERS DFS
by bradikal36`). The **format** is decided by `Game_Type` first, then:

| `Game_Type` | Other conditions, in order | Format |
|---|---|---|
| anything but Classic / a Showdown type | | `Other` (Best Ball, Snake, Madden Classic, Single Stat, **In-Game Showdown**) |
| a Showdown type (`Showdown`, `Showdown Captain Mode`, `KFC Sunday Night Showdown Series`, ...) | | `Showdown` |
| Classic | fee $0 | `Freeroll` |
| | name has `by <user>`, no `NFL`, no `$` | `Private` |
| | name `$N a vs. b`, or exactly 2 entries | `H2H` |
| | name says `Double Up` / `50/50` | `Double Up` / `50/50` |
| | fewer than 100 entries and 1-5 places paid | `Small top-heavy` |
| | `[Single Entry]` / `[1 Entry Max]` | `SE GPP` |
| | `[N Entry Max]` N > 1, or a counter `(x/N)` N > 1 | `N-max GPP` |
| | nothing above | `Other` (listed in the summary so a rule can be added) |

`bankroll.classify_entry` is kept as a **cross-check**: `class_disagreements.csv` lists rows where it and the
format disagree about cash vs GPP (cash = H2H, 50/50, Double Up). It never overrides. The Week 4 bug
(`NFL Single Stat $1 7-Player (Top 3 Win)`, 3 of 7 paid) is `Other`, and has its own test.

## How the field builds (`field.py`)

Per contest, for `all` entries, the `top10` (every entry scoring at least the score of place `ceil(10% x
entrants)`, so ties are included) and `me` (`--me`, counter-stripped). Each measure is over the lineups where it
is defined (`n_resolved`, `n_salary` say how many).

- **Stacking:** `qb_stack1` / `qb_stack2` = QB with 1+ / 2+ same-team **WR or TE** (a RB is not a pass catcher);
  `bringback` = a non-DST, non-QB player from the QB's opponent; `top_stacks` = the most common QB teams among
  stacked lineups (`field_stacks.csv` has the full list).
- **Salary:** `$50,000 - sum`; `avg_unspent`, `share_unspent_1k`.
- **FLEX:** `flex_rb`, `flex_wr`, `flex_te`. **Chalk:** `avg_chalk` = how many of the contest's five most-owned
  players (total `%Drafted` summed over a player's slot rows, DSTs included, ties broken by name) a lineup
  holds. **DST:** `dst_with_qb`, `dst_vs_qb`.
- **Duplicates:** `dup_entries` = lineups in the group whose nine players appear 2+ times *in the whole
  contest*; `dup_groups` = distinct such lineups.
- **Joins.** The standings have no team column, so a lineup player is matched on `player_join`'s normalised
  name + **position** (the slot's; for FLEX the position of his non-FLEX ownership row, else any of RB/WR/TE)
  and the team then comes from the frame. Two frame rows for one name and position are *ambiguous* and a name
  not in the frame is *unmatched*: both go to `field_unmatched.csv`, and the lineup is left out of the measures
  that need him. Showdown contests are parsed and profiled but not analysed here.

## The slate scoring index (`slate_index.py`)

Contests are scored on whatever the games produced, so scores are divided by a per-week index (~1.0 on an
average slate). **Main slate** = the repo's existing definition (`dk_salaries._is_sunday_afternoon`): Sunday
kickoffs 12:00-17:59 ET. A week with fewer than 6 such games has no main slate and no index (Christmas weekend
2022 had 2). **Actual points** come from `results_actual` (real DK scoring, yardage bonuses, points-allowed
tiers), through the existing nflverse loaders. Each candidate is divided by its mean over the season's
complete weeks.

- `top_n_lineup`: slot-weighted sum of the mean actual points of the top-N at each position (QB 12, RB 24,
  WR 36, TE 12, DST 12; QB 1, RB 2, WR 3, TE 1, DST 1, FLEX = the N-weighted mean of RB/WR/TE).
- `p95_optimal`: 95th percentile of 10,000 random lineups from the top of each position (QB 16, RB 32, WR 48,
  TE 16, DST 16), no salary cap (nflverse has no salaries), FLEX from the extra RB/WR/TE draws; seeded by
  (season, week).
- `points_per_game` (my choice): mean combined final score of the main-slate games, the no-player-data baseline.

**Backfill** (`slate_index_backfill.csv`, committed, rebuilt by `python -m dfs.contests.slate_index`): 2021-2025,
89 weeks (2021 added; your history covers it). Per-season spread of the relative index (std): 5-11%, and the
absolute levels of `top_n_lineup` drifted from 151 (2021) to 141 (2025), which is why each season is relative to its
own mean. Seasons outside the backfill (the current one) are fetched on each run; a failure is reported and
those weeks are left out of the fit, never silently scaled.

Caveat: relative to a season mean means 2026's index moves as weeks accrue (it is the mean over weeks played).
The nflverse loaders (`nflverse_results.fetch_*`, the same ones the results loop uses) snapshot the raw files under
`data/raw/` as they always do; the committed backfill means past seasons need no fetch at all.

## Toughness (`toughness.py`)

Per entry: `x` = points / that week's index, `q = (place - 0.5) / entries` (the half place keeps last place
finite; it is `place / entries` to within half a place). Within a **format** (pooled, all its series)

    logit(q) = alpha + beta * x          (weighted least squares, logit clipped to +-6, beta < 0)

and each **series** has its level shifted by `delta_s`, with the slope kept at the format's:
`logit(q) = alpha + delta_s + beta * x`. `delta_s > 0` = the same score finishes worse = a tougher field.

- **Shrinkage:** `delta_s = sum(r) / (n + k)` where `r` is the entry's residual from the format curve, i.e.
  exactly `n/(n+k)` times the series' own mean residual. Tested to equality on noiseless data.
- **`k`: chosen by leave-one-week-out**, as CalPts does: for each (season, week) fit without it, predict that
  week's entries, take the mean absolute error of the finish percentile; grid `0, 1, 2, 5, 10, 20, 50, 100,
  200, 500, 1000, inf`, smallest error wins, ties to the larger `k`. With fewer than 30 entries or 3 weeks it
  falls back to `k = 10` and the summary says so. **I have no real history, so no real `k`.** On the 25-row
  fixture it is the fallback; on a 72-week simulation I built (385 entries, 8 series with known offsets +-0.6)
  it chose `k = 0` (the series genuinely differ and have ~50 entries each) and recovered offsets of +0.57 /
  -0.49 against a true +0.6 / -0.4 (relative to the format's average). That simulation was a one-off, not
  committed; the committed tests check the recoverability on smaller, deterministic sets. Your first real run reports its own `k` in the summary and `toughness_k.csv`.
- **Same-week pairs** (one lineup in several series in one week = identical score and slate): entries sharing
  (format, season, week, points) in 2+ different contests form a group. Each member adds a second equation
  `r_i - mean(r of the group) = delta_s(i) - mean(delta of the group's series)`, which cancels the week's
  slate-index error and the lineup's own luck. **Weight:** `lambda` x the entry's weight, where `lambda =
  var(r) / var(within-group deviation)` clipped to [1, 10] (1 if fewer than 5 groups) - an inverse-variance
  weighting estimated from the data. The prior `k` is added on top, so with no pairs this is exactly the
  formula above. In the paired test (a week shock with sd 1.0 on the logit) the paired series gap lands within 0.1 of the
  truth.
- **Score profiles** (a whole field from a standings file): five points per contest (winner, top 1%, top 10%,
  cash line, median), each worth 0.5 of an entry (they share one contest and one week).
- **Showdown** is fitted separately from Classic and never pooled with it, on raw points (a single game has no
  main-slate index). Classic contests on other slates (Thursday, Sunday night, Monday) are left out, as the
  main-slate index does not describe them. H2H and `Other` have no curve.
- **Outputs** (`toughness_series.csv`): `n`, `n_weeks`, `shrink_weight`, `delta`, `payout_q`,
  `expected_cash_line` (the score, on an average slate, that finishes at the series' own typical cash
  percentile), `format_cash_line` (the same from the format curve) and `toughness` = the difference =
  `-delta / beta` points (positive = tougher). `toughness_formats.csv` has the format curves.
- **H2H** (`h2h_bands.csv`, `h2h_opponents.csv`): win rate by score band of the average-slate score (<100,
  100-120, 120-140, 140-160, 160-180, 180+; a tie, i.e. fee refunded, counts half), and the record per
  opponent with 2+ meetings. W/L/T come from winnings vs fee, not from `Place`.

## Assumptions and judgement calls

Each is a one-line change if you disagree; the first is the one that matters.

1. **The slate index does not predict the cash lines** (above). `SELECTED` is a placeholder, not a finding.
2. `Week` is blank after week 18's Monday (playoffs, offseason): `nfl_calendar` clamps those into week 18.
3. Non-NFL rows are dropped from the log rather than kept with blank NFL columns.
4. In-Game Showdown is `Other`, not `Showdown` (a quarter-long contest on a different scale).
5. A Showdown freeroll is `Showdown`; a Classic freeroll is `Freeroll`. A paid 2-entry Classic with no `vs.` in
   the name is H2H.
6. `Private` = `by <user>` in the name with no `NFL` and no `$`; the trailing `#5` is dropped so weekly
   instances share a series. This rests on the one example you gave.
7. Pass catchers are WR and TE only; the bring-back excludes the DST (that is `dst_vs_qb`); the DST counts as a
   player in the five-most-owned set.
8. Series slope = the format's slope (series have too few entries for their own).
9. Profile points weigh 0.5 each; pair weight is data-driven in [1, 10].
10. Showdown is not normalised by anything (no per-game index); a per-game one could use the `Matchup` column
    kept in the log.
11. The "9-field rows" of a big standings file are handled by padding any short row, not by assuming 9.
12. Cross-format pairs (the same lineup in a Double Up and a GPP) are not used: different formats have
    different baselines.

## What the local session must supply

- **Paths.** `--history` (repeatable, oldest first), `--standings <folder>`, `--out` (default
  `data/contests/`, which is gitignored with the rest of `data/`).
- **The players frame** for field stats: `Name`, `Team`, `Position`, `Opp` (or `Opponent`) and `Salary` - EdgeRaw
  has exactly these (`derived.EDGE_COLUMNS`); pass that week's. `field.field_stats(standings, players, me=...)`
  takes a DataFrame, `dfs contests analyze --players` a CSV of it. Without it, only chalk and duplicates are
  computed.
- **`week close`.** Not wired. The hook is one call after the bankroll sync, failing soft like `results
  update`: `analysis.run([history_csv], CONTESTS_DIR, standings_dir=..., players=<EdgeRaw frame>)` then
  `analysis.write(result)`. It needs a standings folder (a new `--standings-dir` option, or a fixed
  `data/standings/`), which is yours to choose. Standings expire after ~2 weeks, so the hook should run in the
  week the contests finish.
- **The `Contests` tab** can read the CSVs; nothing here writes a sheet.
- Run the engine on the real files once, read the `Other` list and the `class_disagreements.csv`, and add the
  rules those show.

Out of scope and untouched: Sheets, real DraftKings files, any DraftKings call, `src/dfs/model/`, `research/`,
`sim/` (read, not edited), and the Phase 2 "best contest per lineup" EV (after Week 8, locally).
