# The contests engine

`src/dfs/contests/` learns **which contests suit which lineups** and **how your fields build theirs**, from the
two DraftKings files you download by hand and from public nflverse data. Pure Python: no sheet, no credentials,
and **no DraftKings network call of any kind** (standing rule). `dfs contests analyze` is the one command; it is
hidden (`hidden=True`, like `dfs model`) and not in `docs/COMMANDS.md` or the launcher until it is wired into
`dfs week close`. Everything below was built and tested on **synthetic files that match the real formats**
(`tests/contests/fixtures/`, made-up usernames, regenerated by `tests/contests/build_fixtures.py`); no real
DraftKings file has been seen by this code yet.

## Read this first: a public slate index cannot see your cash lines, so weeks are estimated from the data

The first version divided every score by a slate-scoring index built from nflverse and fitted to your five
typed Results `Cash Line`s (GIANT $25 Double Up, 2026 weeks 1-5). **None of the candidates predicts them.**

| Week | Cash line | `top_n_lineup` | `p95_optimal` | `points_per_game` |
|---|---|---|---|---|
| 1 | 147.56 | 1.068 | 1.073 | 1.163 |
| 2 | 140.16 | 0.918 | 0.922 | 0.796 |
| 3 | 158.70 | 1.022 | 1.004 | 1.027 |
| 4 | **105.98** | 1.008 | 1.011 | 0.979 |
| 5 | 153.06 | 0.984 | 0.990 | 1.035 |

(the three right-hand columns are each candidate relative to its 2026 mean over weeks 1-5)

| Candidate | r | R² | Spearman | leave-one-out RMSE | RMSE of "just predict the mean" |
|---|---|---|---|---|---|
| `top_n_lineup` | 0.10 | 0.01 | 0.3 | **24.0** | 23.2 |
| `p95_optimal` | 0.02 | 0.00 | -0.1 | 24.4 | 23.2 |
| `points_per_game` | 0.26 | 0.07 | 0.5 | 27.2 | 23.2 |

Every candidate does *worse* than predicting the mean (last column). A fourth idea (the realised score of
the lineup of players with the best prior form, to measure "did the popular players hit") correlated 0.09
too, so it is not in the code.

**Week 4 is real, not a typo.** The actual standings files show the Oct 4 cash lines were **106.0** (GIANT
$25 Double Up), **106.1** (GIANT $10 Double Up, 2,873 entries) and **108.2** (SE $5 Double Up), on a slate
that is average by every public measure. Cash lines track whether the chalk hit, which no public slate
measure can see. So:

- **The toughness fit does not divide by the index.** It estimates a **week effect** `w_week` from your own
  contests (about 10-15 Classic contests a week identify it), shrunk toward 0, in the same model as the
  series levels. See "Toughness" below.
- `slate_index.py` and its 2021-2025 backfill stay as a **reported context column** (`toughness_weeks.csv`
  shows each week's fitted effect beside the index) and as the `index` comparator in the leave-one-week-out
  comparison of ways to handle the week. `slate_index.SELECTED = "top_n_lineup"` is just the candidate shown.
- Expect the index to stay uncorrelated with `w_week`; the summary prints that correlation each run.

## The two input files

**1. Contest-entry history** (My Contests -> History). One CSV, UTF-8 BOM, 14 columns
(`Sport ... Places_Paid`), the whole account every time. `history.py` keeps every column verbatim as text
(`$8.00`, `2,972`), deduplicates by `Entry_Key` (the export merged last wins), drops non-NFL rows (counted in
`MergeResult.dropped_other_sports`), and adds `Season`, `Week`, `Slate`, `Series`, `Format`, `Matchup`,
`Opponent`, `Entry_No`, `Entry_Max`, `Bankroll_Class`, `Format_Class`. `merge_into(log, export)` is safe to
re-run; exports must be merged **oldest first**, since the last one merged wins (a row with no `Place`, i.e.
a contest still in play, never replaces one that has a result; a column only the log has is kept; the file is
rewritten whenever its content would change, so a changed rule in `series.py` re-labels the whole log).

**2. Per-contest "export full standings"** (`contest-standings-<id>.csv`, bare or in a zip of any name, found
recursively in the `--standings` folder). `standings.py` returns the entries (rank, points, name with `(1/3)`
split off), the score profile, the parsed lineups and (via `ownership.parse_ownership_export`, called as is)
the ownership table. 0-byte files are skipped and listed; a second file for the same contest id is listed and
ignored; a lineup that is not exactly 9 slots (Classic) or CPT + 5 FLEX (Showdown) is reported with its reason
in `lineup_errors.csv` and never guessed. DraftKings serves standings for about two weeks, so download them
promptly: nothing else keeps them.

## Series and formats (`series.py`)

A **series** is a contest's name with the entry counter `(2/5)`, the Showdown matchup `(BUF @ LAR)` and the H2H
opponent stripped (`NFL $1 srwildman vs. rival` -> `H2H $1`; `DREAMERS DFS  by bradikal36 #5` -> `DREAMERS DFS
by bradikal36`). The **format** is decided by `Game_Type` first, then:

| `Game_Type` | Other conditions, in order | Format |
|---|---|---|
| anything but Classic / a Showdown type | | `Other` (Best Ball, Snake, Madden Classic, Single Stat, **In-Game Showdown**) |
| a Showdown type (`Showdown`, `Showdown Captain Mode`, `KFC Sunday Night Showdown Series`, ...) | | `Showdown` |
| Classic | fee $0 | `Freeroll` |
| | name has `by <user>`, does not start with `NFL`, is not "presented by" | `Private` |
| | name `$N a vs. b`, or exactly 2 entries | `H2H` |
| | name says `Double Up` / `50/50` (or `50-50`) | `Double Up` / `50/50` |
| | name says Triple/Quintuple Up, `Nx Booster`, or has a `[Top N Win $X]` bracket | `Multiplier` (`Multiple` column: 3, 5, 10 ... from the name, else prize / fee) |
| | name is exactly `Footballers NFL Weekly Contest` | `SE GPP` (its own series) |
| | `[Single Entry]` / `[1 Entry Max]` | `SE GPP` |
| | `[N Entry Max]` N > 1, or a counter `(x/N)` N > 1 | `N-max GPP` |
| | nothing above | `Other` (listed in the summary so a rule can be added) |

`bankroll.classify_entry` is kept as a **cross-check**: `class_disagreements.csv` lists rows where it and the
format disagree about cash vs GPP (cash = H2H, 50/50, Double Up). It never overrides. The Week 4 bug
(`NFL Single Stat $1 7-Player (Top 3 Win)`, 3 of 7 paid) is `Other`, and has its own test.

## How the field builds (`field.py`)

Per contest, for `all` entries, the `top10` (every entry scoring at least the score of place `ceil(10% x
entrants)`, so ties are included) and `me` (`--me`, counter-stripped). Each measure is over the lineups where it
is defined (`n_resolved`, `n_salary` say how many).

- **Stacking:** `qb_stack1` / `qb_stack2` = QB with 1+ / 2+ same-team **WR or TE** (a RB is not a pass catcher);
  `bringback` = a non-DST, non-QB player from the QB's opponent; `top_stacks` = the most common QB teams among
  stacked lineups (`field_stacks.csv` has the full list).
- **Salary:** `$50,000 - sum`; `avg_unspent`, `share_unspent_1k`.
- **FLEX:** `flex_rb`, `flex_wr`, `flex_te`. **Chalk:** `avg_chalk` = how many of the contest's five most-owned
  players (total `%Drafted` summed over a player's slot rows, DSTs included, ties broken by name) a lineup
  holds. **DST:** `dst_with_qb`, `dst_vs_qb`.
- **Duplicates:** `dup_entries` = lineups in the group whose nine players appear 2+ times *in the whole
  contest*; `dup_groups` = distinct such lineups.
- **Joins.** The standings have no team column, so a lineup player is matched on `player_join`'s normalised
  name + **position** (the slot's; for FLEX the position of his non-FLEX ownership row, else any of RB/WR/TE)
  and the team then comes from the frame. Two frame rows for one name and position are *ambiguous* and a name
  not in the frame is *unmatched*: both go to `field_unmatched.csv`, and the lineup is left out of the measures
  that need him. Showdown contests are parsed and profiled but not analysed here.

## The slate scoring index (`slate_index.py`)

**Context only** (see the top of this file). A per-week index (~1.0 on an average slate) of how high the main
slate scored. **Main slate** = the repo's existing definition (`dk_salaries._is_sunday_afternoon`): Sunday
kickoffs 12:00-17:59 ET. A week with fewer than 6 such games has no main slate and no index (Christmas weekend
2022 had 2). **Actual points** come from `results_actual` (real DK scoring, yardage bonuses, points-allowed
tiers), through the existing nflverse loaders. Each candidate is divided by its mean over the season's
complete weeks.

- `top_n_lineup`: slot-weighted sum of the mean actual points of the top-N at each position (QB 12, RB 24,
  WR 36, TE 12, DST 12; QB 1, RB 2, WR 3, TE 1, DST 1, FLEX = the N-weighted mean of RB/WR/TE).
- `p95_optimal`: 95th percentile of 10,000 random lineups from the top of each position (QB 16, RB 32, WR 48,
  TE 16, DST 16), no salary cap (nflverse has no salaries), FLEX from the extra RB/WR/TE draws; seeded by
  (season, week).
- `points_per_game` (my choice): mean combined final score of the main-slate games, the no-player-data baseline.

**Backfill** (`slate_index_backfill.csv`, committed, rebuilt by `python -m dfs.contests.slate_index`): 2021-2025,
89 weeks (2021 added; your history covers it). Per-season spread of the relative index (std): 5-11%, and the
absolute levels of `top_n_lineup` drifted from 151 (2021) to 141 (2025), which is why each season is relative to its
own mean. Seasons outside the backfill (the current one) are fetched on each run; a failure is reported and those
weeks are left out of the `index` comparison only (nothing else uses the index).

Caveat: relative to a season mean means 2026's index moves as weeks accrue (it is the mean over weeks played).
The nflverse loaders (`nflverse_results.fetch_*`, the same ones the results loop uses) snapshot the raw files under
`data/raw/` as they always do; the committed backfill means past seasons need no fetch at all.

## Toughness (`toughness.py`)

Per entry: `x` = the score as scored (raw points), `q = (place - 0.5) / entries` (the half place keeps last
place finite), `y = logit(q)` clipped to ±6. One ridge least-squares fit:

    y = alpha_F + w_week + delta_s + beta_F * x

- `alpha_F`, `beta_F`: the **format** curve (pooled over its series, not shrunk; `beta < 0`).
- `delta_s`: the **series** level; `delta_s > 0` = the same score finishes worse = a tougher field. Shrunk by
  `n/(n+k)`. The slope is the format's (a series has too few entries for its own).
- `w_week`: the **week effect**, shared by every contest in the week: how much tougher or softer the whole
  week played than the model expects for a score. Shrunk by `n/(n+k_w)`. **Estimated within a format group:**
  every Classic main-slate format shares one `w_week` per week; Showdown has its own, on its own contests.
- The shrinkage is exact in the sense the old one was: with only series effects `delta_s = sum(r)/(n+k)` for
  the entry residuals `r`, and likewise `w_week` with `k_w`. Tested to equality on balanced noiseless designs.
- **Same-week pairs** (one lineup in several contests in a week) are the special case where the score term
  cancels; the week effects make a separate weighting unnecessary, so there is none. `pair_entries` in the
  series table still counts them.
- **Score profiles** (a whole field from a standings file) add five points per contest (winner, top 1%, top
  10%, cash line, median) at 0.5 of an entry each.
- **Showdown** is its own format with its own week effects, on raw points, never pooled with Classic. Classic
  contests on other slates (Thursday, Sunday night, Monday) are left out (their week is not the main slate's).
  H2H and `Other` have no curve.

### `k`, `k_w`, and which treatment of the week

`k` and `k_w` are chosen by **leave-one-week-out**, as CalPts does: for each (season, week) refit without it,
predict that week's entries, take the mean absolute error of the finish percentile. **A week that has not been
played has no week effect, so the held-out prediction uses `w = 0`.** Grids: `k` in `0, 1, 2, 5, 10, 20, 50,
100, 200, 500, 1000, inf`; `k_w` in `0, 1, 2, 5, 10, 20, 50, 200, inf` (`inf` = no such effect). Smallest error
wins; ties go to the larger penalties. With fewer than 30 entries or 3 weeks it falls back to `k = k_w = 10`.

The engine compares three ways of handling the week by that same error, each at its own best penalties, on
the same rows (those the index covers), picks the lowest, and writes all three to `toughness_models.csv`
(and the summary):

| Treatment | What it does |
|---|---|
| `raw` | raw points, no week effects |
| `index` | points divided by the main-slate slate index, no week effects |
| `weeks` | raw points plus week effects (its grid contains `raw`: `k_w = inf`) |

Ties (to 1e-9) go to the simplest in that order. Two honest caveats: `weeks` has the largest grid, so its error
is the most optimistic of the three by a little; and because an unplayed week's effect is unknown, **`weeks` can
barely beat `raw` on this out-of-week error** - what it buys is cleaner format and series estimates (the week
shock no longer leaks into them) and the week table itself. The comparison is the safeguard: where the score
really does scale with an index, `index` wins.

**Results.** I have no real history here, so the numbers below are from a seeded simulation
(`tests/contests/simulate_compare.py`: 4 seasons, 403 Classic entries, 8 series with known levels, a week
shock with sd 1.0 on the logit, about 20 points like the swing in your cash lines, and a slate index
unrelated to it):

| Treatment | best `k` | best `k_w` | leave-one-week-out error |
|---|---|---|---|
| `raw` | 10 | inf | 0.1555 |
| `index` | 5 | inf | 0.1641 |
| `weeks` | 10 | 0 | **0.1541** |

The week effects came back with sd 0.90 against a true 1.0 and a correlation of 0.00 with the index. In the
opposite world (`--index-matters`: points really scale with the index) the same code picks `index`
(0.0579 vs 0.0868 raw, 0.0865 weeks). The committed tests assert both orderings. **Your first real run
reports its own three numbers, `k`, `k_w` and the choice.** At about 3,200 entries and 40 series the whole fit
takes about 11 seconds.

### Outputs

- `toughness_series.csv`: `n`, `n_weeks`, `shrink_weight` (`n/(n+k)`), `delta`, `payout_q`,
  `expected_cash_line`, `format_cash_line`, `toughness` (`-delta/beta` points; positive = tougher),
  `pair_entries`.
- **`expected_cash_line` is the score that finishes at the series' own typical cash percentile in an average
  week, `w = 0`.** Week effects cannot predict a week before it is played, so every forward-looking number
  uses `w = 0`; `toughness_weeks.csv` shows how far real weeks moved from it (`w` in logit, `w_points` in
  points at the group's pooled slope, positive = a tougher week, plus the `slate_index` context).
- `toughness_formats.csv` (curves, `expected_cash_line` at the format's typical payout), `toughness_models.csv`
  (the three-way comparison), `toughness_k.csv` (the penalty grid of the treatment used).
- **H2H** (`h2h_bands.csv`, `h2h_opponents.csv`): win rate by band of the **raw** score (<100, 100-120,
  120-140, 140-160, 160-180, 180+; main-slate Classic only; a tie, i.e. fee refunded, counts half), and the
  record per opponent with 2+ meetings. W/L/T come from winnings vs fee, not from `Place`.

## Assumptions and judgement calls

Each is a one-line change if you disagree.

1. **Weeks are estimated, not looked up** (above): the slate index is context and a comparator, never a divisor
   unless the leave-one-week-out comparison says `index` is best. All Classic main-slate formats share one
   week effect; Showdown has its own.
2. `Week` is blank after week 18's Monday (playoffs, offseason): `nfl_calendar` clamps those into week 18.
3. Non-NFL rows are dropped from the log rather than kept with blank NFL columns.
4. In-Game Showdown is `Other`, not `Showdown` (a quarter-long contest on a different scale).
5. A Showdown freeroll is `Showdown`; a Classic freeroll is `Freeroll`. A paid 2-entry Classic with no `vs.` in
   the name is H2H.
6. `Private` = `by <user>` in a name that does not start with `NFL` (a `$` amount in it is fine; "presented by" is not a creator); the trailing `#5` is dropped so weekly
   instances share a series. This rests on the one example you gave.
7. Pass catchers are WR and TE only; the bring-back excludes the DST (that is `dst_vs_qb`); the DST counts as a
   player in the five-most-owned set.
8. Series slope = the format's slope (series have too few entries for their own).
9. Profile points weigh 0.5 each. The week effects replace the separate same-week-pair weighting.
10. Showdown uses raw points and its own week effects (no per-game index; a per-game one could use the
    `Matchup` column kept in the log).
11. The "9-field rows" of a big standings file are handled by padding any short row, not by assuming 9.
12. Expected cash lines are for an average week (`w = 0`); the held-out error that picks `k`, `k_w` and the
    treatment also uses `w = 0`, so it scores how well the curves predict a week not yet played.
13. H2H bands use raw points.

## How it is wired locally (Phase 1)

`dfs week close` runs the contest step after the bankroll reconciliation (soft: a failure is printed and the close still
succeeds); `dfs contests update [--csv] [--sheet-id] [--no-sheet]` is the same step alone. `contests_close.run_contests` does, in order:

1. **History.** The export is the `--csv`, else the **newest file in `[contests] downloads_dir`** (default `~/Downloads`) whose **header
   row** has the DraftKings history columns (`capture.find_history_export`; the name is ignored) and the run says which. A copy goes to
   `data/raw/dk_history/` (`capture.keep_history_copy`: dated, never overwriting a different file of the same name, skipped when an
   identical one is already there). `bankroll sync` also keeps the copy and merges the log.
2. **Standings.** `capture.capture_standings` **moves** every new `contest-standings-<id>.csv` (or zip holding one, any name) from Downloads to
   `data/raw/dk_standings/`. A contest already kept stays in Downloads ("already kept"); a 0-byte file is reported as a failed or
   expired download and left. The reminder is printed each time: standings expire after about two weeks.
3. **The engine** over the log and every kept file (`analysis.run` + `analysis.write`, outputs in `data/contests/`; the default location, not
   `data/contest_log.csv`). Field stats need each contest's week of players: `week_frames` builds them from the **last DraftKings salary
   snapshot in `data/raw/draftkings/` before that week's Sunday 1:00 pm ET lock** whose games are on that Sunday, main slate only (Sunday
   kickoffs 12:00-17:59 ET), with the opponent from `Game Info`. On the first real run all 20 standings files resolved every lineup
   player (0 unmatched), including Week 2's Hundo.
4. **Ownership.** Each kept standings file's `%Drafted` is appended to `data/ownership_log.csv` (replacing that contest's rows) when the
   contest is not logged yet or sits under a different week. Report-only: nothing reads it to change `Own%` or `Lev`.
5. **Cash Line** (`contests_cash_line`, live sheet only): a **blank** Results `Cash Line` for a week is filled from the standings cash line of
   `[contests] cash_line_series` (default the GIANT $25 Double Up, which matches the values Sam typed for Weeks 4 and 5); a typed value is
   never overwritten, and a typed value more than 0.5 off the standings is printed beside it.
6. **The `Contests` tab** (`sheet_contests`, `docs/SHEET_REFERENCE.md`).

Toughness on the tab: the first real run showed the engine's leave-one-week-out choice of `k` and `k_w` shrinks **every** series and week effect
to nothing (`k = 1e9`, `k_w = inf`: a held-out week has `w = 0`, so week effects cannot help that error, and series offsets are small against
the noise), so the engine's per-series toughness is +0.0 for all. The tab therefore shows the real within-week gap in cash lines between series of
one format (`sheet_contests.peer_gaps`) and says the engine's number is not separable yet.

Out of scope and untouched: Sheets, real DraftKings files, any DraftKings call, `src/dfs/model/`, `research/`,
`sim/` (read, not edited), and the Phase 2 "best contest per lineup" EV (after Week 8, locally).
